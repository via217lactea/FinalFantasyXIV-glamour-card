# FF14 투영 카드 메이커

파이널판타지14의 장비·투영 세트를 한 장의 이미지 카드로 만들어 공유하는 도구.
한국어 / 일본어 / 영어를 지원한다.

**배포는 [DEPLOY.md](DEPLOY.md) 참고.** 아이콘을 스프라이트로 굽지 않으면 Cloudflare Pages가
배포를 거부한다.

## 데이터 계층

Lodestone은 CORS 헤더를 주지 않고 HTML 구조도 자주 바뀌므로 런타임에 긁지 않는다.
대신 빌드 시점에 데이터마이닝 CSV를 병합해 정적 JSON으로 굽는다.

| 언어 | 출처 | 방언 |
|---|---|---|
| en, ja | `xivapi/ffxiv-datamining` (`csv/en`, `csv/ja`) | oxidizer (헤더 1행) |
| ko | `Ra-Workspace/ffxiv-datamining-ko` (`csv/`) | SaintCoinach (헤더 3행) |

두 리포는 컬럼 **순서**가 다르므로 항상 이름으로 접근한다. 아이템 ID는 지역 공통이라
그것만으로 3개 언어가 조인된다.

### 외형 전용 시트

안경과 패션 아이템은 **Item이 아니다.** `EquipSlotCategory`가 없어서 장비 루프가 전혀
보지 못한다. 각자 다른 시트에서 온다.

| 슬롯 | 시트 | 이름 컬럼 | 수량 |
|---|---|---|---|
| `facewear` (안경) | `Glasses` | `Name` | 708 |
| `ornament` (패션 아이템) | `Ornament` | `Singular` | 55 |

둘 다 염색할 수 없어 `dyeCount`는 0이다. **ID 공간이 Item과 겹치지만** 슬롯별로 파일이
나뉘어 있어 앱에서는 모호하지 않다 — URL 공유를 붙일 때 슬롯을 함께 인코딩해야 한다.

안경 아이콘은 `200001~200744`로 일관되지만, 패션 아이템은 `786~8057`로 대역이 다르다.
폴더 계산은 동일하게 동작하니 추출물에 있으면 잡히고, 없으면 `missing-icons.json`에 뜬다.

### 알려진 함정

- 한국 리포의 `Stain.csv`는 이름 행이 데이터와 어긋나 있다 (`Name` 자리가 `uint32`).
  타입 행이 정답이므로 `csv.ts`가 첫 `str` 컬럼으로 자동 재정렬하고 경고를 찍는다.
- `EquipSlotCategory`의 값 `1`은 착용, `-1`은 해당 부위를 **가림**을 뜻한다.
  후자는 `hidesMask`로 보존한다 (로브가 다리를 덮는 등, 투영 카드에서 의미 있는 정보).
- 허리(6.0에서 폐지)와 영혼결정은 제외한다.

## 명령

```bash
npm run build:data                        # public/data/* 재생성
npm run icons:plan                        # 필요한 ui 명령 출력
npm run build:icons -- --from <추출폴더>   # icons/* 채우기 (로컬 전용)
npm run build:sprites                     # icons/ → public/sprites/*.png
npm run build:versions                    # 한/글섭 패치 버전 기록
npm run check:icons                       # 부족한 아이콘 목록 산출 (추출물 불필요)
npm run fill:icons                        # 빠진 것만 Lodestone에서 보충
npm run build:sprites                     # public/icons → public/sprites (배포용)
```

## 아이콘

아이콘은 게임 클라이언트 안에 들어 있는 자산이라 데이터마이닝 리포에 없다. 직접 꺼내야 한다.

### SaintCoinach.Cmd 란

게임 설치 폴더의 압축된 자산에서 이미지를 꺼내 PNG로 저장해 주는 작은 콘솔 프로그램이다.
설치 과정은 없고 압축을 풀어 실행 파일을 더블클릭하면 검은 명령창이 뜬다. **윈도우 전용**이며
게임이 설치돼 있어야 한다.

1. https://github.com/xivapi/SaintCoinach/releases 에서 `SaintCoinach.Cmd.zip` 다운로드
2. 압축을 풀고 `SaintCoinach.Cmd.exe` 실행
3. 처음 실행하면 게임 설치 경로를 묻는다 (보통
   `C:\Program Files (x86)\SquareEnix\FINAL FANTASY XIV - KOREA` 또는 글섭 설치 폴더)
4. 아래 명령으로 필요한 구간만 뽑는다

```bash
npm run icons:plan   # 지금 카탈로그에 맞는 ui 명령을 출력
```

`ui`는 번호 범위를 받는다. 우리 아이콘은 몇 개 구간에 몰려 있어 **약 2.5만 번만 훑으면**
되는데, 그냥 `ui`만 입력하면 100만 번대까지 전부 뽑느라 스무 배쯤 오래 걸린다.

끝나면 `2026-08-28` 같은 날짜 폴더가 생긴다. 그 안의 `ui/icon`을 가리켜:

```bash
npm run build:icons -- --from "<날짜폴더>/ui/icon"
npm run check:icons                       # 부족한 아이콘 목록 산출 (추출물 불필요)
npm run fill:icons                        # 빠진 것만 Lodestone에서 보충
npm run build:sprites                     # public/icons → public/sprites (배포용)
```

수집기는 필요한 것만 골라 `icons/{폴더}/{아이콘ID}.png`로 복사하고, `_hr1`
고해상도 변종이 있으면 그쪽을 우선한다 — 내보내기를 2~3배로 하므로 40px 원본은 눈에 띄게
뭉갠다.

**자체 호스팅이 필수다.** 외부 도메인 이미지를 캔버스에 그리면 tainted 상태가 되어 PNG
내보내기가 실패한다.

### 스프라이트

```bash
npm run build:sprites   # icons/ → public/sprites/
npm run check:sprites   # 매니페스트·시트 일치와 배포 파일 수 검증
```

아이콘은 개별 파일이 아니라 **스프라이트 시트로 배포한다.** Cloudflare Pages 무료 플랜의
배포 파일 상한이 20,000개인데 아이콘만 19,000개가 넘어, 패치 두어 번이면 배포가 막힌다.
시트로 묶으면 **331개**로 떨어진다.

| | 개별 파일 | 스프라이트 |
|---|---|---|
| 배포 파일 수 | 18,516 | 331 |
| 검색 결과 60개 | 요청 60건 | 요청 1~2건 |
| 카드 14칸 | 42KB | 최대 2MB (대개 훨씬 적음) |

설계 결정 두 가지.

**시트는 작게(64개) 묶는다.** 크게 묶으면 카드 한 장 보려고 수 MB를 받고, PNG 내보내기가
참조된 시트를 **요소마다 한 번씩** 이미지에 인라인한다. 작은 시트가 양쪽 비용을 모두 낮춘다.

**시트 안 배치 순서를 검색 정렬과 똑같이 맞춘다.** 아이템 레벨 내림차순이라 검색 결과 첫
페이지가 시트 한두 장에 몰린다. 이 점에서는 개별 파일보다 오히려 낫다.

**아이콘 원본(`icons/`)은 `public/` 바깥에 둔다.** `public/` 아래 있는 것은 정의상 전부
빌드에 복사되므로, 원본이 거기 있으면 배포 파일 수가 그대로 돌아온다. `icons/`는 git에서
제외하고 **`public/sprites/`를 커밋한다.**

> Gamer Escape의 *Dictionary of Icons* 페이지에는 이 아이콘들이 없다. 그쪽은 직업·퀘스트·
> 지도 마커 같은 UI 아이콘(060000 대역 이상)을 다루는 수작업 문서다.

### 패치가 나올 때마다 다시 추출해야 하나

아니다. 아이콘 ID는 뒤에 붙기만 하고 기존 것이 바뀌지 않으므로 **전체 추출은 한 번이면
된다.** 이후 패치는 신규 아이템 수백 개만 늘어나고, 그건 주간 워크플로가 알아서 처리한다.

```
build:data  →  check:icons  →  fill:icons  →  PR
```

`check:icons`는 카탈로그와 `public/icons/`를 대조할 뿐이라 게임 클라이언트가 필요 없다.
러너에서 돌아간다는 뜻이다. 한 패치에 800개 넘게 늘어나면 `fill:icons`가 거부하는데,
그건 직접 다시 추출할 때가 됐다는 신호다.

아이콘 약 73MB는 저장소에 커밋한다. 한 번 커밋한 뒤로는 패치마다 수백 KB만 늘어난다.

```bash
npm run fill:icons                 # missing-icons.json 에 있는 것만
LODESTONE_REGION=jp npm run fill:icons
```

### Lodestone을 주 소스로 쓰지 않는 이유

아이콘 URL이 콘텐츠 해시라 아이콘 ID로 만들어낼 수 없다.

```
https://lds-img.finalfantasyxiv.com/itemicon/30/30a2109c…png?n7.55
```

따라서 아이콘 1장당 상세페이지 1회 + 이미지 1회가 든다. 18,588장 전부라면 수만 건의
요청과 수 GB의 HTML을 주고받아 73MB를 얻는 셈이고, 그러고도 커버리지는 93.3%다
(Lodestone에 항목이 없는 장비가 1,935개). `?n7.55` 쿼리가 패치마다 바뀌므로 캐시도
오래 못 간다. 그래서 `fill:icons`에는 800개 상한이 걸려 있다 — 빈틈용이지 카탈로그용이
아니다.

Lodestone ID 매핑은 [Asvel/ffxiv-lodestone-item-id](https://github.com/Asvel/ffxiv-lodestone-item-id)를
쓴다 (게임 ID → 줄 번호).

**자체 호스팅이 필수다.** 외부 도메인 이미지를 캔버스에 그리면 tainted 상태가 되어
PNG 내보내기가 실패한다.

> Gamer Escape의 *Dictionary of Icons* 페이지에는 이 아이콘들이 없다. 그쪽은 직업·
> 퀘스트·지도 마커 같은 UI 아이콘(060000 대역 이상)을 다루는 수작업 문서다.

## 출력

```
public/data/
  meta.json          슬롯 정의, UI 슬롯 12칸, 아이템 분류 112종
  stains.json        염색 125색 (hex + 3개 언어 이름)
  items/{slot}.json  슬롯별 아이템 (11개 파일)
```

아이템은 정확히 한 슬롯에만 속하므로 샤딩에 중복이 없다. 에디터는 첫 진입에
`meta` + `stains`(약 7KB)만 받고, 슬롯을 열 때 해당 파일만 가져온다.

## PNG 내보내기

```bash
npm run check:export   # 폰트가 내보내기까지 도달하는지 검사
```

`html-to-image`가 카드 DOM을 SVG `foreignObject`로 직렬화해 래스터화한다. 여기서 두 가지가
따라온다.

**1. 폰트는 인라인 임베딩해야 한다.** SVG는 격리된 상태로 렌더되므로 URL로 참조된 폰트는
도달할 수 없다. 이때 대체 서체로 떨어지는 게 아니라 **네모 상자로 나온다.** 라이브러리가
자체 임베딩을 제공하지만 `document.styleSheets`를 훑는 방식이라 **교차 출처 스타일시트에서
조용히 실패한다** — `cssRules` 접근이 SecurityError를 던지고 라이브러리가 이를 삼킨다.
우리 폰트는 둘 다 외부 출처이므로 CSS 텍스트를 직접 받아 처리한다.

`check:export`가 세 고리를 검사한다. 레지스트리의 폰트가 실제로 로드되는지, 로드된
스타일시트가 내보내기 필터에 걸리는지, 각 토큰이 등록된 패밀리로 해석되는지. 어긋나면
화면은 멀쩡한데 저장된 파일만 깨지므로, 눈으로 발견하기 어렵다.

**2. 캔버스 오염을 피해야 한다.** 다른 출처의 이미지를 그리면 내보내기가 예외를 던진다.
아이콘을 같은 출처에서 서빙하고 스크린샷을 data URL로 읽는 이유가 이것이다.

그 밖의 처리:

- **2회 렌더 후 두 번째 결과 사용.** 사파리가 첫 `foreignObject` 래스터를 리소스 정착 전에
  그려 빈 이미지를 내놓는 알려진 문제를 피한다. 첫 회는 폰트 캐시도 덥힌다.
- **표시용 transform 일시 해제.** 에디터는 카드를 컬럼 폭에 맞춰 축소해 보여주는데, 그
  상태로 직렬화하면 축소가 결과물에 박힌다. 내보내는 동안 해제하고 `CardStage`의
  `ResizeObserver`는 `isExporting()`으로 멈춘다.
- 해상도 1×/2×/3× (960 / 1920 / 2880px). 기본은 2×.
- 파일명은 코디명과 캐릭터명에서 만들고 파일시스템 금지 문자를 제거한다.

## URL 공유

```bash
npm run check:share   # 왕복·길이·포맷 안정성 검사
```

카드 상태를 바이트로 직렬화해 base64url로 URL 조각(`#c=...`)에 담는다. JSON은 한 벌 옷만
담아도 천 자를 넘지만 이 방식은 **평균 115자, 14칸을 다 채워도 222자**다. 채팅에 붙여넣을
수 있어야 하므로 이 차이가 결정적이다.

바이트 배치:

```
1  버전
2  채워진 슬롯 비트마스크
n  슬롯 순서대로: 아이템 ID(varint), 염색1, 염색2
1  템플릿 인덱스
1  플래그 — 비율, 염색 표기, 카드 테마, 다국어 표기
1  카드 언어
n  길이 접두 UTF-8 문자열 4개: 코디명, 캐릭터, 서버, 직업
```

**슬롯 비트마스크가 ID 모호성을 없앤다.** 안경과 패션 아이템은 자체 시트에서 오고 ID가
Item 시트와 겹치므로, ID만으로는 무엇을 가리키는지 알 수 없다. 마스크에서의 위치가 그것을
결정한다.

**쿼리스트링이 아니라 조각(fragment)을 쓴다.** 조각은 서버로 전송되지 않으므로 공유된
코디가 링크를 가진 두 사람 사이에만 머문다.

**스크린샷은 담기지 않는다.** 축소한 JPEG도 base64로는 수십 KB라 어떤 URL 한계도 넘는다.
링크는 코디를 나르고, 받는 사람이 자기 스크린샷을 올린다. UI가 이 점을 안내한다.

링크를 열면 사용 중인 슬롯의 카탈로그 샤드만 받아온다. 세 부위짜리 코디가 전체 카탈로그를
끌어오지 않는다. 현재 데이터에 없는 ID는 건너뛰고 나머지는 살린다.

`check:share`에 **고정 샘플 링크**가 들어 있다. 버전을 올리지 않고 바이트 배치를 바꾸면 이게
디코딩에 실패한다 — 인코더와 디코더를 함께 고쳐 왕복 검사가 통과하는 경우에도 잡힌다.
이미 배포된 링크가 깨지는 순간이 바로 그 지점이다.

## 미리보기 아티팩트

```bash
npm run build:preview    # dist-preview/glamour-card-preview.jsx
```

`preview/template.jsx`에 `preview/sample-data.json`을 주입해 단일 파일로 만든다. 디자인
검토용이며 실제 앱과 별개다 (아이콘 폴더를 참조할 수 없어 아이콘은 항상 대체 프레임으로
나온다).

빌드가 끝나면 장비 2개짜리 카드와 **14칸을 모두 채운 카드**를, **스크린샷까지 넣은 상태로**
서버 렌더링해 검사한다. 카드가 가장 빡빡한 건 전부 채웠을 때이고, 2개짜리로는 줄어들지
않는 행을 영영 발견할 수 없다 — 실제로 그래서 넘침 버그가 검사를 두 번 통과해 나갔다. 조건부로만 그려지는 가지는 그 조건을 만들어 주지 않으면 검사가
스치고 지나간다 — 실제로 이미지가 없을 때만 렌더하다 보니 `<img>` 분기 안의 미정의 변수를
놓쳐 출시한 적이 있다.
**빈 카드만 보고 통과시키면 안 되기 때문이다** — 실제로 한 번, 슬롯을 채워야만 드러나는
회귀를 놓친 적이 있다. 미리보기는 타입 검사가 없는 순수 JSX라 실제 앱이라면 컴파일에서
막혔을 오류가 그대로 통과한다. 그래서 `density()`는 없는 키를 읽으면 예외를 던진다.
React는 `undefined` 스타일 속성을 조용히 버리므로 출력물만 훑어서는 잡히지 않는다.

## 패치 버전

`public/data/versions.json`에 한국·글로벌 패치 버전을 기록한다. 화면 언어가 한국어면
한섭 버전을, 일본어·영어면 글섭 버전을 보여준다 — 한섭 클라이언트는 패치가 뒤처지므로
한국어 사용자에게 글섭 번호를 보여주면 틀린 정보가 된다.

- **한국**: 데이터마이닝 리포가 패치마다 git 태그를 단다 (`v7.55`). 인증 없이 태그 피드에서
  읽는다. 정확하다.
- **글로벌**: 어느 리포에도 기계가 읽을 수 있는 버전 문자열이 없다. Lodestone이 아이템
  아이콘 URL에 붙이는 캐시 무효화 표식(`...png?n7.55`)이 라이브 패치를 따라가므로 아이템
  페이지 하나를 읽어 거기서 뽑는다. **공식 버전 문자열이 아니라 파생 신호이므로**, 값이
  틀리면 `data/version-override.json`에 적어 덮어쓴다.

가져오기에 실패해도 이전 값을 유지한다. 일시적 네트워크 오류로 화면의 버전이 사라지면 안 된다.

### 서체

| 폰트 | 라이선스 | 용도 | 지원 |
|---|---|---|---|
| Pretendard | SIL OFL 1.1 | 본문 | 한·일·영 |
| Gowun Batang | SIL OFL 1.1 | 표제 명조 | 한·영 |
| Bodoni Moda | SIL OFL 1.1 | 룩북·스프레드 제호 | 영 |
| IBM Plex Sans (+ KR, JP) | SIL OFL 1.1 | 코디명·서명 | 한·일·영 |

```bash
npm run check:fonts                       # 후보 폰트의 실제 다운로드 용량 측정
npm run check:fonts -- "Nanum Myeongjo"   # 특정 폰트만
```

**본문은 Pretendard로 확정한다.** IBM Plex를 검토했으나 채택하지 않았다. Plex는
`IBM Plex Sans` / `Sans KR` / `Sans JP` 세 패밀리로 쪼개져 있어 3개 언어를 덮으려면
스택을 쌓아야 하는데, KR과 JP의 기준선이 각각 22%와 12%로 달라 한 줄에 섞이면 높이가
어긋난다. 제작사(산돌)가 의도된 설계이며 수정하지 않겠다고 밝힌 사안이다. 우리 카드의
보조 이름 줄은 `Neo Queen's Tiara / ネオクイーン・ティアラ`처럼 항상 혼합이라 이 문제를
매번 만나게 된다. Pretendard는 한 패밀리가 한·일·영을 모두 덮는다.

**코디명과 서명은 IBM Plex를 쓴다.** Plex는 스크립트별로 패밀리가 갈리므로
`IBM Plex Sans` / `Sans KR` / `Sans JP` 세 개를 스택으로 쌓는다. KR과 JP의 기준선이
각각 22%와 12%로 달라 **본문에는 쓸 수 없지만**, 제목과 이름은 한 번에 한 언어라 두
기준선이 한 줄에서 만나지 않는다. 미리보기 빌드가 Plex가 장비 목록으로 새지 않는지
검사한다 (`title face stays out of the list`).

템플릿별 적용 위치:

| 템플릿 | 위치 |
|---|---|
| 기본 카드 | 코디명(32px), 캐릭터·서버·직업 줄(14px) |
| 룩북 | 모델 이름(30px). 컬렉션 라벨은 자간 넓은 대문자라 제외 |
| 매거진 표제 | 코디명(20px), 하단 서명 줄(11px) |
| 패션 스프레드 | 부제 옆 서명 줄(16px). 괘선 박스는 7.5px라 제외 |

**라이선스 조건이 하나 더 있다.** PNG 내보내기는 폰트를 링크하지 않고 **데이터를 인라인
임베딩**한다. 따라서 "웹폰트 링크는 허용, 파일 임베딩은 불가" 같은 조건이 붙은 폰트는
쓸 수 없다. SIL OFL이면 전부 가능하다.

무료 폰트를 구할 곳:

- **Google Fonts** — 전부 OFL. 한국어 필터 제공
- **눈누** (noonnu.cc) — 한국어 폰트가 많지만 **OFL이 아닌 자체 라이선스가 섞여 있다.**
  웹폰트 불가·임베딩 불가 조건이 붙은 것들이 있으므로 개별 확인이 필수다
- **Fontshare** — 라틴 전용, 품질이 좋다

한글 폰트는 글자 수가 수천 자라 통째로 받으면 수 MB다. 반드시 **동적 서브셋**이나
`unicode-range` 분할로 서빙해야 한다. Google Fonts와 Pretendard의 dynamic-subset 빌드는
둘 다 이 방식이다. `check:fonts`가 한글 청크 용량을 따로 뽑아주므로 그 값으로 판단하면
된다.

#### 폰트 추가하기

1. 라이선스 확인 (OFL 또는 임베딩 허용 명시)
2. `npm run check:fonts -- "폰트명"`으로 한글 청크 용량 확인
3. `index.html`에 스타일시트 링크 추가
4. `src/lib/fonts.ts`에 출처·라이선스와 함께 등록
5. `src/index.css`의 토큰에 연결하거나, 특정 템플릿에서만 쓴다면
   `fontFamily`로 직접 지정

### 테마

기본값은 **밝은 테마**다.

- **밝게**: 오프화이트. 순백(`#fff`)은 넓은 밝은 면에서 눈이 부시므로 아주 살짝 낮췄고,
  그래도 흰색으로 읽힌다
- **어둡게**: 완전한 검정 대신 부드러운 근사 검정. 순검정 위의 흰 글씨는 번져 보인다

종이 질감은 `feTurbulence` SVG를 **data URI로 인라인**한다. PNG 내보내기는 외부 자산을
가져올 수 없으므로 외부 파일이면 질감이 통째로 빠진다.

질감은 **`.paper::before` 한 겹에만** 올린다. `.paper` 자체에 `background-image`를 주면
투명도를 걸 수 없어 노이즈가 원래 강도로 깔리고, 그 위에 오버레이가 사본을 한 겹 더 쌓는다.
어두운 배경에서는 화면 잡음처럼 보였다. 어두운 테마는 `multiply` 대신 `screen`으로 섞어
질감이 그을음이 아니라 결로 보이게 한다. `check:export`가 이 규칙을 검사한다.

토큰은 색이 아니라 역할로 이름을 붙였다 (`surface` / `fg` / `rule`). 덕분에 같은 클래스가
두 테마에서 그대로 동작하고, 바뀌는 건 `[data-theme]`에 걸린 CSS 변수뿐이다.

```bash
npm run check:theme   # 카드가 화면과 다른 테마를 가질 수 있는지 검증
```

**팔레트 별칭(`--color-*`)은 `[data-theme]`이 붙는 모든 요소에서 다시 선언해야 한다.**
커스텀 속성 안의 `var()`는 **선언된 자리에서** 치환되고, 그렇게 확정된 값이 자손에게
상속된다. `--color-surface: var(--c-surface)`를 `:root`에만 두면 페이지의 팔레트가 그 안에
굳어버리고, 카드가 자기 `data-theme`으로 `--c-surface`를 바꿔도 별칭은 다시 보지 않는다.
카드는 조용히 화면 테마를 따라간다. **소스만 봐서는 드러나지 않고 렌더해야만 보이는**
종류의 버그라, `check:theme`이 빌드된 CSS의 변수 연쇄를 브라우저와 같은 방식으로 풀어
검증한다.

첫 방문은 `prefers-color-scheme`을 따르고 이후 선택은 저장된다. **카드는 화면과 별개로
테마를 가질 수 있다** — 밝은 타임라인에 어두운 카드를 올리고 싶을 수 있고, 그 반대도 있다.
카드가 `data-theme`을 자기 노드에 다시 선언하므로 변수만 새로 잡히고 나머지는 그대로다.

### 템플릿

카드 디자인은 **레지스트리 항목**이다. 추가하려면 `src/card/templates/`에 컴포넌트를 쓰고
`src/card/registry.ts`에 등록하면 끝이고, 나머지는 손댈 필요가 없다.

```
src/card/
  types.ts              템플릿이 받는 데이터 계약
  registry.ts           목록
  templates/
    shared.tsx          염색 표기 등 공통 조각
    plain.tsx
    editorial.tsx
```

`CardPreview`가 슬롯 정렬, 언어 폴백, 높이 측정을 모두 끝내서 넘긴다. 템플릿은 **보이는
방식만** 정한다.

레지스트리 항목에는 `languages`가 있다. 짧은 라틴 이름을 전제로 짠 레이아웃은 긴 한국어
이름에서 무너질 수 있어서, 검증하지 않은 언어를 고르면 선택기에 표시가 뜬다.

염색 표기(색상 칩 / 이름만)는 템플릿과 **독립**이다. 어느 조합이든 성립한다.

선택기는 썸네일 그리드이며, **썸네일은 저장된 이미지가 아니라 카드를 작게 렌더한 것**이다.
템플릿과 어긋날 수 없고, 자산이 필요 없고, 남의 코디가 아니라 지금 편집 중인 코디가 보인다.

현재 템플릿은 셋이다.

| id | 성격 |
|---|---|
| `plain` | 아이콘과 색상 칩이 있는 평범한 카드 |
| `editorial` | 룩북 지면. 트림 마크·바코드·스파인 텍스트. 머리말은 코디명 → 캐릭터 → 서버·직업 순 |
| `masthead` | 매거진 표제. Didone 대문자 제호, 괘선, 사이즈 태그, 염색 바 |
| `spread` | 패션 스프레드. 좌측 상단 대형 제호 + 3칸 괘선 박스 + 볼드 산세리프 부제 |

`spread`가 따라간 참고 자료는 사진을 두 장 싣지만 **한 장으로 만들었다.** 이 레이아웃의
성격은 이미지 개수가 아니라 제호 블록과 괘선 박스에서 나오므로, 스크린샷 하나가 오른쪽
전체를 차지해도 인상이 유지된다. 다중 이미지 슬롯은 별도 작업으로 남겨둔다.

`masthead`와 `spread`는 라틴 표제에 **Bodoni Moda**를 쓴다. 고대비 디돈이 아니면 표제로 읽히지
않는다. 한글·일본어 본문은 그대로 Gowun Batang / Pretendard다.

### 스크린샷 자리와 염색 표기

**스크린샷 자리는 이미지가 없어도 비워 둔다.** 이미지가 없을 때 그 칸을 아예 빼면 "사진이
없는 완성된 디자인"처럼 보여서, 사진이 들어갈 곳이라는 신호가 사라진다. 자리를 잡아두면
업로드 전에 카드의 실제 레이아웃을 볼 수 있다. 모든 템플릿이 `ImageSlot` 하나를 공유한다.

**카드 전체 염색 띠는 제거했다.** 코디의 모든 색을 모아 보여주던 막대인데, 스크린샷과
주목도를 두고 경쟁했다. 색은 각 장비 항목에 붙고, 카드에는 개수만 남는다.

### 룩북 형식

카드 형식은 두 가지다. `plain`은 아이콘과 색상 칩이 있는 평범한 카드, `editorial`은
패션 룩북 지면을 흉내낸다.

룩북 형식의 규칙은 참고 자료를 따랐다.

- 모서리 **트림 마크**(재단선), 헤어라인 괘선, 넓은 여백
- **아이콘 없음** — 지면의 이미지는 스크린샷 하나뿐이다
- 다른 언어 이름이 **위**, 주 언어 이름이 **아래**에 크게
- 염색은 색상 칩이 아니라 `순백색 | 칠흑색` 텍스트
- 오른쪽 가장자리 세로 스파인 텍스트, 하단 바코드

트림 마크와 바코드는 **생성된 도형**이다. 이미지 파일을 쓰면 PNG 내보내기에서 사라진다.
바코드는 코디명과 캐릭터 이름으로 시드를 만들어 코디마다 다르게 나오되 같은 입력이면
항상 같은 막대가 나온다 — 글자 하나 칠 때마다 막대가 재배열되면 안 된다. 스캔되지 않는
장식이며 아무것도 인코딩하지 않는다.

스퀘어에닉스 로고 마크는 넣지 않는다. 저작권 표기는 이용 조건상 필요하므로 텍스트로 넣는다.

### 카드 크기와 글씨 맞춤

카드는 항상 **960px 폭**으로 렌더링된다. 뷰포트와 무관하게 고정이라 내보내는 결과물의
해상도가 화면 크기에 따라 달라지지 않는다. 화면에는 `CardStage`가 CSS transform으로
축소해 보여줄 뿐이다 — transform은 레이아웃 박스를 바꾸지 않으므로 바깥 크기를 측정한
높이로 직접 지정해야 한다.

높이는 선택한 비율로 **고정**이고, 대신 목록의 글씨가 줄어들어 들어간다. 3개 언어 이름에
염색 이름까지 붙으면 한 항목이 3줄이 되므로, 카드가 세로로 자라게 두면 비율이 무의미해진다.

배율은 계산이 아니라 **측정**한다. 이름이 크기에 따라 다르게 줄바꿈되므로 행 높이가 글씨
크기의 선형 함수가 아니다. 실제 레이아웃을 상대로 이진 탐색을 몇 번 돌리면 수렴한다
(`fitScale`). 순수 함수로 분리해 브라우저 없이 테스트한다.

배율은 **위아래 양쪽**으로 찾는다. 항목이 적으면 1.35까지 키워 목록이 박스 바닥에
닿게 하고, 많으면 줄인다. 어느 쪽이든 목록이 배정된 세로 공간을 꽉 채워, 카드가 덜 그려진
것처럼 보이지 않는다.

**목록 안의 모든 치수는 em이어야 한다.** 맞춤 과정은 목록의 `font-size`만 바꿔서 높이를
재는데, px로 잡힌 값은 그때 따라 줄지 않는다. 그러면 측정 결과와 실제 렌더가 어긋나고,
행 높이가 아이콘에 의해 바닥이 잡혀 글씨만 줄여서는 절대 들어가지 않는다. 실제로 아이콘이
px여서 14칸이 넘치는 버그가 있었다. 미리보기 빌드가 행 안의 px 사용을 검사한다
(`row sizes only in em`). 목록 루트의 `font-size`만 예외이며, 그것이 곧 배율을 거는 값이다.

높이는 `scrollHeight`가 아니라 `getBoundingClientRect().height`로 잰다. 전자는 소수점을
버리고 마지막 자식의 아래 여백을 세지 않아, 행이 여남은 개 쌓이면 그 부족분이 넘침으로
드러난다.

측정은 **웹폰트가 로드된 뒤 다시 한다.** 폰트 도착 전에 재면 대체 서체의 치수를 읽게 되고,
이후 글자가 커지면서 "맞는다"고 측정된 박스를 넘쳐도 다시 잴 기회가 없다. 실제로 이
누락 때문에 항목이 잘려 보이는 버그가 있었다. `document.fonts.ready`와 `ResizeObserver`
양쪽에 재측정을 건다.

### 확인 대화상자

`window.confirm` / `alert` / `prompt`는 **쓰지 않는다.** 샌드박스 프레임에서는 차단되어
`undefined`를 반환하므로, 그 반환값으로 분기하는 코드는 조용히 실행되지 않는다. 실제로
전체 초기화 버튼이 이것 때문에 동작하지 않았다. 확인이 필요하면 버튼 자리에서 인라인으로
처리한다. 미리보기 빌드가 이 호출을 검사한다 (`no blocking dialogs`).

### 목록 용량

```bash
npm run check:capacity   # 템플릿·비율별로 몇 개가 들어가는지 계산
```

행 안의 모든 치수가 em이므로 행 높이가 글씨 크기에 **정비례**하고, 따라서 브라우저 없이
산술로 용량을 구할 수 있다. 카드 높이에서 템플릿별 고정 장식을 빼면 목록에 쓸 수 있는
높이가 나오고, 그걸 하한 배율의 행 높이로 나누면 최대 개수다.

항목이 늘면 배율만 줄이는 게 아니라 **행이 줄을 접는다.**

| 밀도 | 조건 | 동작 |
|---|---|---|
| 0 | 7개 이하 | 이름 / 보조 이름 / 염색이 각각 한 줄 |
| 1 | 8~10개 | 염색 이름이 보조 줄로 합쳐짐 |
| 2 | 11개 이상 | 보조 줄까지 이름 옆으로 접힘 |

14칸을 전부 채우면 세 줄짜리 행이 16:9 카드에 절대 들어가지 않는다. 글씨를 읽을 수 없는
크기까지 줄이느니 줄을 접는 편이 낫다.

가장 빡빡한 16:9 기준 용량: 기본 카드 13, 룩북 12, 매거진 표제 11, 스프레드 15.
정사각형이나 4:3은 세로가 더 길어 항상 여유가 있다.

임계값(`CardPreview`의 `density`)과 이 모델은 **함께 움직여야 한다.**

배율에는 **하한 0.56**이 있다. 카드는 내보낼 때 2~3배로 확대되므로 화면에서 작아 보여도
결과물에서는 읽힌다. 12칸을 전부 채우고 3개 언어에 염색까지 켜면 16:9에는
읽을 수 있는 크기로 들어가지 않는다. 그때는 40%까지 줄이는 대신 카드가 그만큼 자란다 —
비율을 포기하는 편이 가독성을 포기하는 것보다 낫다.

### 디자인 원칙

염색이 디자인 시스템이다. 사용한 염색들이 카드 상단에 색 띠로 쌓이고, 그중 가장
정체성이 뚜렷한 색(채도가 높고 명도가 중간대인 것)이 UI 강조색이 된다. 염색을 하나도
안 하면 띠는 나타나지 않고 강조색은 황동색으로 돌아간다.

카드 표기 언어는 화면 언어와 분리돼 있다. 한국어 UI로 작업하면서 카드만 영어로 뽑아
해외 커뮤니티에 공유하는 흐름이 실제로 흔하다.

`CardPreview`는 상호작용 요소를 담지 않는다. PNG 내보내기가 이 노드를 그대로 캡처한다.

### 스크린샷

업로드한 이미지는 **반드시 data URL로 보관한다.** `URL.createObjectURL`이 만드는 `blob:`
소스는 내보내기 시점에 캔버스를 오염시켜 PNG 저장을 실패시킬 수 있다. 업로드 즉시 긴 변
1600px로 축소해 JPEG로 인코딩한다 — 4K 스크린샷을 원본으로 들고 있으면 pixel ratio 3
내보내기에서 브라우저가 멈춘다.

투영 스크린샷은 캐릭터가 화면 중앙에 있는 경우가 드물어서 `object-position`을 드래그로
지정할 수 있게 했다. 이미지가 없으면 카드는 단일 열로 떨어지고 염색 띠는 상단으로 간다.

## 배포

Cloudflare Pages 무료 플랜 기준이다.

```bash
npm run build:sprites   # public/icons → public/sprites (아이콘 추출 후 한 번)
npm run check:deploy    # 빌드 후 호스트 한도 검사
```

### 아이콘을 스프라이트로 묶는 이유

**Cloudflare Pages 무료 플랜은 배포당 파일 20,000개가 한계다.** 카탈로그가 쓰는 아이콘만
약 19,300개라, 낱개로 올리면 **한도의 97%**를 차지하고 여유가 몇백 개뿐이다. 패치 한두 번이면
넘친다.

`build:sprites`가 40px 칸으로 이루어진 시트 몇 장으로 묶고, 어느 칸인지를 `index.json`에
기록한다. 파일 수가 스무 개 남짓으로 줄고, 장비 12개짜리 카드가 요청 12번이 아니라 한 번으로
끝난다.

`public/icons`는 시트를 만드는 **원본**이지 배포 대상이 아니다. `.gitignore`에 들어 있고,
Vite 플러그인이 빌드 결과에서 `dist/icons`를 지운다. `check:deploy`가 이 규칙과 파일 수·
파일 크기를 함께 검사한다.

### 처음 배포하기

1. [Cloudflare 대시보드](https://dash.cloudflare.com) → **Workers & Pages** → **Create** →
   **Pages** → **Connect to Git**
2. 저장소를 연결하고 빌드 설정을 넣는다

   | 항목 | 값 |
   |---|---|
   | Framework preset | None (또는 Vite) |
   | Build command | `npm run build` |
   | Build output directory | `dist` |

3. **Save and Deploy**

`public/sprites`와 `public/data`는 저장소에 커밋되어 있어야 한다. 아이콘 원본은 커밋하지
않는다 — 시트만 있으면 된다.

### 저장소에 커밋할 것

```
public/data/       카탈로그 JSON (약 3.6 MB)
public/sprites/    아이콘 시트 + index.json
```

`public/icons/`는 커밋하지 않는다. 다른 PC에서 작업하거나 저장소를 새로 받으면 시트만
가져오면 되고, 아이콘을 다시 추출할 필요는 없다.

### 패치가 나오면

주간 워크플로가 `build:data → check:icons → fill:icons`를 돌려 PR을 연다. 아이콘이 새로
들어오면 `build:sprites`를 다시 돌려 시트를 갱신해야 한다.
